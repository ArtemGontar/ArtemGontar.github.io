🧩 Aligning definitions, not teaching them

Six terms, five stops

🔌

MCP

Model Context Protocol — a server exposing tools/resources over a standard interface. Loaded whole, every turn.

🎒

Skills

Packaged, on-demand instructions the agent loads only when a task matches — pointer first, body on demand.

🐴

Harness

The runtime/loop (CLI, IDE ext., cloud agent) that turns a raw model into an actor with tools and memory.

🪝

Hooks

Pre/post tool-call interception — filter, block, or rewrite behavior before it costs you a turn.

🧩

Context Engineering

Deliberately curating what enters the context window — the discipline behind every tip tonight.

💾

Prompt Caching

Reusing a stable prefix so repeated context is billed once, not re-sent every single turn.

01 · Model selection

Pick the model the task needs — not a default

My own default under tight budgets: Claude Sonnet (mid) or GPT-5.6 Luna at high reasoning — escalate only when the task actually stalls.
TierAnthropicOpenAIBest for
Cheap $HaikuGPT-5.6 LunaMechanical edits, formatting, triage — or budget mode at high reasoning
Mid $$SonnetGPT-5.6 TerraDay-to-day implementation, well-specified features
Frontier $$$Opus / FableGPT-5.6 SolGenuinely ambiguous architecture, hard debugging — when budget allows
🔥

The habit trap: reaching for the frontier model out of habit, for a task the cheap tier finishes in 2 seconds.

  • Decide by task complexity, never by "always pick the best available"
  • Stuck after repeated failed attempts → escalate one tier, don't multiply turns on the same model
  • Escalating one tier and succeeding first try is usually cheaper than 3 retries on the cheap tier
  • De-escalate too: once a frontier model produces a plan, hand the mechanical execution back to a cheap/mid model

🗓️ A real week

  • Luna/Haiku: renaming a field across 40 files, writing a changelog entry, triaging 20 GitHub issues
  • Sonnet/Terra: implementing a well-specified feature end-to-end, writing tests, most PR-sized work
  • Opus/Fable/Sol: a genuinely ambiguous migration plan, a production incident with no obvious cause
Anti-pattern to avoid: leaving the harness on auto-router permanently. Auto-routing helps if your habit is defaulting to a frontier model for everything — it saves you from yourself. But once you understand each model's real cost and ability, manual routing beats auto every time.

01 · Model + harness

The harness is part of the model choice

HarnessTax: 21 model–harness pairs across SWE-bench Lite and Terminal-Bench 2.0. The same model can land at a very different cost depending on the runtime around it.

🧪 What the study measured

7 models × 3 harnesses — Claude Code, Codex CLI, and Pi — on the same 30 tasks, three runs per task, using official benchmark evaluators.

~2.0×Claude Code cost vs. Pi on SWE-bench Lite
±2%Average harness effect on SWE-bench Lite success
9 / 12Alternative harnesses had the best observed success
  • Pi reaches the Pareto frontier on both benchmarks with four core tools: read, write, edit, and bash
  • Claude Code's first context is over 10× Pi's on average — the harness tax can start before the task begins
  • On Terminal-Bench 2.0, Claude Code costs about 1.5× Pi across shared models, while success stays within roughly ±5%
A default harness can be a hidden harness tax. Benchmark the model × harness pair, not the model alone.

CLI beats MCP — almost always

Same job, two integration shapes: an MCP server exposes every tool schema up front and pays for it every turn, a CLI is read once and then just called — the benchmark below is what that difference costs in practice.

📐

Why it wins

17 real GitHub tasks × 5 repeats, same model, LLM-judged success. CLI wins tokens, cost, and success rate.

⚙️

The mechanism

MCP schemas are loaded into context on every turn, whether the turn uses them or not. A CLI's help text is read once, then the agent just calls it.

🧪

Early but usable

"axi" (Agent eXperience Interface) CLIs like gh-axi and chrome-devtools-axi wrap existing CLIs with agent-tuned output — still early, but already usable in production harnesses.

3× the tokens, 2× the turns, and a 16-point lower success rate — the "convenience" of always-on MCP tools is not free.

Skill-first beats always-on MCP and prompt bloat

🎒 Popular skill use cases

  • Parsing/generating a file format (PDF, XLSX, DOCX) — loaded only when that file type shows up
  • House code-review standards or commit conventions — one Skill, reused across every repo
  • An ops runbook (incident triage, release checklist) — procedural steps, not re-read prose
🔌

MCP

Always-loaded schemas. Cost paid every turn, used or not.

📜

Long prompt

Static instructions baked in, relevant or not.

🎒

Skills

Loaded only on match — pointer first, full text on demand.

Skill-first: ship the repetitive/complex knowledge (a runbook, a house style, a tool's rules) as a Skill before reaching for an always-on MCP server or prompt bloat.

03 · Token-reduction playbook

Context engineering: isolate, then cap

🧑‍🚀 Subagents isolate context

Each subagent gets its own context window — 50 files read, 30 commands run, two failed attempts — none of that noise reaches the parent. Only the final result crosses back.

🔍 ToolSearch trims the MCP tax

Instead of loading every MCP schema up front, the agent searches a tool index and pulls in only the schema it needs. Cuts the eager-load tax (175,757 → 153,621 tokens/task, slide 6) — better than nothing, still short of a CLI's 46,462.

🔥 1M context ≠ better context

  • MRCR v2: even Opus 4.6 drops 91.9%→78.3% from 256K to 1M — every model degrades, none holds flat
  • Weaker models fall off a cliff: GPT-5.4 79.3%→36.6% (128K→1M)
  • Keep working context at 250–400K tokens — retrieval accuracy is the real ceiling

A local CLI proxy that rewrites verbose shell output (git, test runners, package managers, k8s) into a lean equivalent before the agent ever sees it. Runs transparently in front of your normal shell — no change to how you invoke commands, only to what reaches the model's context.

Headroom — compress on the wire

Code search (100 results)
21%
SRE incident debugging
57%
Codebase exploration
42%
GitHub issue triage
30%
⚙️

How it works — four compression passes

  • Structural dedup: repeated JSON/YAML keys, boilerplate stack-frame lines, and near-identical log rows collapse to one representative + a count
  • Re-encoding: deeply nested JSON gets rewritten as a flatter, less punctuation-heavy format (see JSON→TOON below) — same data, far fewer tokens per field
  • Salience-aware truncation: the FATAL/ERROR line and its neighbors survive byte-for-byte; surrounding noise gets summarized or dropped
  • Semantic chunking for RAG: retrieved passages are trimmed to the sentences that actually match the query, not the whole source document
📦

package.json example

A generated lockfile or huge package.json re-encoded from JSON to TOON-style rows removes repeated "key": punctuation per entry — the exact same dependency data, a fraction of the tokens.

Accuracy held flat on GSM8K/TruthfulQA/SQuAD/BFCL in Headroom's own evals — compression, not summarization; nothing is guessed.

03 · Token-reduction playbook

Don't let the cache write itself twice

Cache hits are billed far cheaper than fresh input tokens — but the cache is fragile. Two habits quietly destroy it:

  • Switching providers mid-session — the cache is provider- and often model-specific; hopping between Claude/GPT/Gemini rewrites it from zero every time
  • Letting a task straddle the TTL window — come back after a break and you pay full write price to rebuild the same prefix
Rule of thumb: a cache read runs ~10× cheaper than a fresh input token. The 1.25–2× write premium pays for itself after just one reuse.
1×Uncached fresh input token
1.25–2×Cache write premium (paid once)
0.10×Cache read cost (paid on every reuse)
ProviderDefault TTLExtended TTLCache writeCache read
Anthropic Claude5 min1 hr (paid)1.25× (5 min) / 2.0× (1 hr)0.10× — 90% off
OpenAI~5–10 min≤ 1 hrno premium — automatic0.10× — 90% off
Gemini~10 min (proxy-level)—varies by proxydiscounted, provider-set

💰 Worked example — Claude Sonnet 4.6, $3/M standard input

A 50K-token system prompt/repo-context reused 20 times in one session, 5-min TTL:

  • No caching: 20 × 50K × $3/M = $3.00
  • With caching: 1 write (50K × $3.75/M) + 19 reads (50K × $0.30/M) = $0.19 + $0.29 = $0.48 — an 84% reduction
  • Same 50K tokens spread across 2 providers instead of 1 → two full-price writes, most of that saving disappears

04 · Observability

Don't monitor tokens — notice when the agent drifts

🧠 Context pressure

Watch context % and cache-hit ratio. When it climbs, /compact, checkpoint, or start a new task — a bigger window ≠ a healthier session.

🔥 Burn rate

Watch tokens/cost per minute. A spike means stop watching it "think harder" and inspect what actually changed — exploration and tool loops compound fast.

🔁 Retry loops

Same tool called repeatedly, same file reread, same command failing — that's a signal to intervene manually. Three failed attempts need a new strategy, not a fourth prompt.

The goal isn't fewer tokens. It's noticing diminishing returns early enough to change course — treat context/burn rate like CPU temperature, not a monthly invoice.

📟 Ambient telemetry beats a monthly report

Claude Code's /usage and a custom statusline put model, context %, cache ratio, and session cost in front of you while you work — no dashboard to open. Community statuslines add burn-rate and RTK savings too.

04 · Observability

From session cost to per-PR attribution

🧾 cc-ledger — a concrete demo, not a product

Hooks record every prompt/edit locally to SQLite, then roll it up per PR: cost, AI-line count, category split (coding vs. exploration vs. retries), and runaway-session detection (p50/p95/p99 spend). Young project, few stars — treat it as proof the idea works, not an established tool.

🔭 Build your own, or don't start from zero

Claude Code and other harnesses already export tokens, cost, commit.count, and pull_request.count via OpenTelemetry — enough to pipe into Langfuse, Grafana, or your own collector and tag by git branch/PR# yourself.

🔎 agentsview — smarter cross-agent analysis

One local ledger across Claude Code, Codex, and other coding agents: daily/per-model token & cost breakdown, peak context, session history — a good starting point if you'd rather adopt than build.

Sessions tell you what the agent did. Git branch/PR metadata tells you why it was worth it — that correlation is still an open, unsettled part of this tooling space.

Spend is right-skewed, not fixed

Most of the gap between median and heavy spenders isn't "more work done" — it's unsupervised agent loops multiplying context overhead. A bigger token budget doesn't fix a bad task-routing decision; it just delays noticing it.

Don't ask "Can AI do this?" Ask "Is this the best use of my remaining budget?"
